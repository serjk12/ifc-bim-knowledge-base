## In plain words

This is the person who writes software around IFC and Revit: a web developer building a browser viewer, a Python scripter extracting data from models, a C# engineer making a Windows tool, a Revit add-in or Dynamo / pyRevit author, a pipeline engineer converting IFC to glTF or a database, and increasingly the person writing an **MCP server** so that an AI assistant can talk to a BIM model. They are comfortable with code and bad at construction vocabulary, which is the reverse of the engineers on the other pages.

Their libraries: **IfcOpenShell / Bonsai** (Python, C++), **web-ifc and That Open / IFC.js** (JavaScript / WebAssembly), **xBIM** (C# / .NET), plus Revit API with Dynamo, pyRevit and macros, IfcConvert, Three.js, Cesium, Unity, QGIS, SQLite / DuckDB. Typical output: a script, a converter, a viewer, a checker, a plug-in, an MCP tool.

For an MCP/LLM tester this persona is both an **end user** (asks the assistant to write or run code, or to inspect a file in developer terms) and a **peer** (reports problems in MCP servers themselves: "send_code_to_revit returns Method not found", `en-revit-auto-r029`). Many of their messages are bug reports with versions, code and numbers.

## Goals

- **Open any real export without a crash or a timeout**, and get geometry identical to a commercial viewer ("BIMvision shows it fine"): `en-gh-thatopen-r017`, `en-beginner-qa-r010`.
- **Deterministic, memory-bounded pipelines** that run on a server or in a browser tab (`en-gh-thatopen-r013`, `en-gh-xbim-others-r014`, `ja-japan-r011`).
- **Correct world coordinates and units** for every element, including mapped items (`en-gh-xbim-others-r001`, `zh-csdn-dev-r002`).
- **Keep the link between IDs**: GlobalId in IFC, UniqueId / ElementId in Revit, `expressID` in the parser (`ja-coord-r014`, `ja-qiita-guid-r026`, `zh-zhihu-r014`, `en-dynamo-pyrevit-s002`).
- **Cheap data access** without opening the heavy authoring software: reading values from partners' big or old models (`ja-japan-r014`).
- **AI assistants that do real BIM work reliably**: tools that return real errors, don't claim success without saved state (`en-aimcp-r002`, `ja-japan-r010`).

Plain-language bridge: the developer treats IFC as a graph of typed objects in a text file (STEP format), with a few hundred object types and a lot of optional fields. What they are missing is the "why" behind a real-world model: a clash, a sleeve, a storey, an as-built update. ## How to role-play this persona in tests

**Voice.** Terse and technical. A bug-report register: symptom first, version and numbers next, sometimes code or a stack trace, rarely a greeting or thanks. Class and method names appear verbatim (`IfcMappedItem`, `GetFlatMesh`, `IsTypedBy`, `get_psets`, `create_shape`). Benchmarks as numbers: "12 MB: 222 s vs 2 s", "400 MB", "300000 components". Frequently comparative: "BIMvision shows it fine", "xBIM is faster". English example: *"load 300mb ifc in web-ifc runs out of memory in browser, any tricks"* (`en-stackoverflow-s011`); Russian: *"смени класс у IfcBuildingElementProxy с именем Колонна* на IfcColumn вместе с типом, чтоб не сломать валидацию"* (`ru-habr-dev-s008`); Chinese: *"把模型里所有IfcWall的属性集都读出来，导成csv，列要有GlobalId、Name、Pset_WallCommon里的IsExternal和FireRating"* (`zh-csdn-dev-s001`); Japanese: *"400MBのIFCをlazyで開いて壁だけ数えて。メモリどれくらい使った？"* (`ja-fs-s013`). Self-described newcomers also exist: "I am completely new to both BIM and IfcConvert".

**Typical context.** A named library and version, an operating system or runtime (Node, browser, .NET, Python, Revit year), a file size and a repro. Frequently mentions a reference tool that behaves differently. When the context comes from an AI-tool chain, expects the assistant to **run** something and report measured results (counts, memory, time), not just advise.

**Knowledge level.**
- Strong: programming, data structures, performance, build tools, packaging, WebAssembly, Revit API calls.
- Medium: IFC schema concepts they have met in their own code (inverse attributes, representation maps).
- Weak: the construction meaning of classes and properties; why a property set exists; practical BIM workflows; national requirements; vocabulary of any trade.
- Believes: any odd output is a bug in the library; the file is valid if the header says so. Reluctant to share the model (confidentiality; `en-gh-thatopen-r003`).

**What to test with this persona.**
- Concrete facts from a real file: entity counts, storey list, mapped-item counts, largest elements by triangle count (`en-dev-s001`, `en-dev-s003`).
- Safe write: change class / add pset / delete types on a copy, then validate (`ru-habr-dev-s008`, `en-psets-s004`).
- Encoding: reports of `\X2\` sequences; correct decoding to the real text, no re-encoding of other lines (`zh-err-s006`, `enc-s008`).
- Large files: use of lazy loading, subsetting, streaming; honest reporting of memory and time rather than a guess.
- Version/header consistency (`en-dev-s009`).
- Revit side: batch export with API, UniqueId to IFC GUID mapping (`en-dynamo-pyrevit-s002`, `ja-guid-s012`).

**Quick judge checklist.**
- Did the assistant actually inspect the file (counts, names, versions) or just recite documentation?

- Does it separate "file is invalid" from "library cannot handle it"?
- Are there honest limits: memory, WASM 4 GB ceiling, schema versions it cannot read?
- For writes: new file, validation step, and a list of what changed?
