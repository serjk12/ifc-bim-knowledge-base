# Coordinates, georeferencing, units, levels/storeys and spatial structure

Topics covered (vocabulary): `coordinates_georef`, `units`, `levels_storeys`, `spatial_structure`.
Evidence base: 285 real records (240 distinct source pages) and 185 synthetic prompts carrying at least one of these four topic tags. Language of the real records: en 242, zh 18, ru 6, ja 5, it 4, nl 4, de 3, es 3 (the `lang` field of the record; a few "de"/"es" records only keep an English paraphrase, see the notes in the Real questions section). There are no real records in Korean, French, Portuguese or Norwegian and only six in Russian (mostly video lesson titles), so the Korean, French, Portuguese, Norwegian and most Russian prompts below are synthetic, built on English/Chinese real patterns, and are labelled as such.

## In plain words

An IFC file is a model **plus a set of "where is zero?" and "what is the ruler?" statements**. Three things decide whether a model shows up in the right place, at the right size, on the right floor:

1. **Where is zero and how far did the model drift from it?** Every wall sits in a chain of placements (element -> storey -> building -> site -> project). Somewhere in that chain a hidden offset can be buried, and Revit users meet it as "my IFC lands 2 km away from the architect's model". See [Geometry, placement, coordinates, georeferencing and units](../../01_ifc_basics/06_geometry_placement_coordinates_units.md) sections 2-4.
2. **Is the model tied to a real-world map system?** IFC4 can store a map conversion (`IfcMapConversion` + `IfcProjectedCRS`, ideally an EPSG code). IFC2x3 cannot, so people use property sets or `IfcSite` latitude/longitude, which is only an approximation. Revit has its own words for this (Internal Origin, Project Base Point, Survey Point, Shared Coordinates); IFC has none of them, which is why "shared coordinates" questions never end. See the Revit side in [Revit IFC export reference](../../03_software/revit/ifc_export_reference.md) (Coordinate Base) and [Revit IFC import and link reference](../../03_software/revit/ifc_import_link_reference.md) (section 5).
3. **What are the units, and which floor does an element belong to?** Units are declared once per project (mm, m or feet) and everything else is read through them. Floors are `IfcBuildingStorey` objects, and an element belongs to a storey through a containment relationship, not by its height. Revit only makes a storey out of a level flagged "Building Story", so elements can silently land on a lower storey. See [Spatial structure and relationships](../../01_ifc_basics/04_spatial_structure_and_relationships.md) and the vocabulary in the [glossary](../../08_glossary/glossary_multilingual.md).

For an AI assistant connected to an IFC or Revit model these are "read, compare, explain" tasks (list storeys, find the offset between two files, report the unit) and a few risky "write" tasks (move a model, set a CRS, reassign a storey). The most common failure of assistants is answering with a confident story before reading the actual numbers in the file.

**How people write about this.** English posts are short and symptom-first ("model lands miles away", "levels at double height", "ocean in QGIS"), often with software and version only ("Revit 2025", "exporter 25.4"), and many are GitHub issues pasted as titles. Chinese and Russian posts are usually "how do I set base point / survey point / absolute coordinates" with a video or forum answer. Dutch, German and Italian sources are guideline-style (ILS, BIM-Basis, Biblus) and talk about "nulpunt", "Projektnullpunkt", "origine". Users rarely say "IfcMapConversion"; they say "coordinates", "georef", "shared coordinates", "origin", "north", "level", "floor".

## Problems in depth

### 1. Models do not line up (federation)

**Symptoms in users' words.**
- (it) "i modelli IFC non si sovrappongono, uno è fuori di km, dove imposto origine e coordinate del sito prima di esportare?" (EN: IFC models do not overlap, one is km away; where do I set origin and site coordinates before export?) [src](https://biblus.acca.it/ifc-coordinate-system/)
- (zh) "链接的各个模型基点不一致怎么办" (what if the linked models' base points are inconsistent?) [src](https://www.jianshu.com/p/409188142cfa); "群楼每人建一栋，测量点基点怎么设才能定位拼起来" (several people model separate podium buildings, how to set survey and base point so they fit) [src](https://zhidao.baidu.com/question/1755259387786621668.html)
- (en) "Site IFC exported with survey point and building IFC exported with shared coordinates; True North rotation gets applied twice when assembled." [src](https://github.com/Autodesk/revit-ifc/issues/301)
- (nl) federations "go wrong because models do not share the same zero point" [src](https://github.com/OpenAEC-Foundation/OpenAEC-BIM-validator/issues/21)
- (en) "Georeferenced IFC files look right in Trimble/BIMvision but linking them in Revit 2022 puts them wrong." [src](https://github.com/Autodesk/revit-ifc/issues/566)

**Why it happens.** Each authoring tool decides what "zero" means when it writes the file. Revit can export from Internal Origin, Project Base Point, Survey Point or Shared Coordinates (see [export reference](../../03_software/revit/ifc_export_reference.md), General tab). If the architect exported from the base point and the engineer from shared coordinates, the files differ by the base-point-to-survey-point distance, and a True North angle may be added a second time. Other tools behave differently again: in a Civil 3D thread the explanation was that Civil 3D uses absolute coordinates while Revit uses the project base point [src](https://forums.autodesk.com/t5/civil-3d-forum/export-ifc-wrong-position/td-p/11945739).

**What fixes it.** One coordinate agreement for all disciplines (Dutch guideline example: origin outside the building near the first grid intersection, optional reference object, georeference stored as a model property) [src](https://www.digigo.nu/ilsen-en-richtlijnen/bim-basis-ils/3-2-lokale-positie); export all files with the same base; check with a shared object (grid, column); fix in the receiving tool only as a last resort, because it has to be repeated on every model update [src](https://github.com/Autodesk/revit-ifc/issues/566).

**A good assistant should:** (1) load every file and, per file, report the length unit, the 3D context (WorldCoordinateSystem, TrueNorth), `IfcMapConversion`/`IfcProjectedCRS` (or IFC2x3 psets), `IfcSite` placement and RefLatitude/RefLongitude, and the bounding box of elements in metres; (2) compute the offset vector and rotation difference between files; (3) say which file differs from the agreed reference; (4) only then suggest a fix. **Clarifying questions:** Which model is the reference? Which Revit Coordinate Base did each author use (or which software)? Is there an agreed CRS/EPSG in the BEP? Do you want a read-only report or should I shift one file?

### 2. Revit Link IFC / Open IFC places the model wrong

**Symptoms in users' words.**
- "Why does Revit not give an option for Positioning when linking IFC files?" [src](https://forums.autodesk.com/t5/revit-architecture-forum/why-does-revit-not-give-an-option-for-positioning-when-linking/td-p/12331165) (answer in the thread: the link is internal origin to internal origin).
- "Is there a way to import an IFC using the Revit project base point as an origin?" [src](https://github.com/Autodesk/revit-ifc/issues/320) (later answer: supported for Link IFC from Revit 2026: Internal Origin, Project Base Point, Survey Point plus orientation).
- "Link IFC in Revit 2025-2027 positions geometry higher than it should be and creates levels at twice the elevation. Open IFC is fine." [src](https://github.com/Autodesk/revit-ifc/issues/990)
- "Linking the IFC and linking the cached .ifc.rvt give different project-north rotations." [src](https://github.com/Autodesk/revit-ifc/issues/710)
- (es) Spanish help text for the same problem: opening/linking gives no choice of coordinate system [src](https://emea.support.arkance.world/hc/es/articles/36464850969234-Using-IFC-files-with-a-Shared-Coordinates-system) (record keeps an English paraphrase).
- (zh) "ifc导入revit之后三维视图里什么都看不到" (after importing IFC nothing is visible in 3D; checks listed: visibility, phase filter, huge coordinates, view range) [src](https://zhidao.baidu.com/question/341569640619976845.html)

**Why it happens.** `Link IFC` historically maps the IFC origin to Revit's Internal Origin; Revit 2026 added positioning choices. The importer also turns the IFC's rotation into Revit true north and, in Revit 2025-2027, a reported duplicated Z offset places levels twice as high (Autodesk ticket REVIT-237045; a fix is listed in release 27.3.0.12 per [import reference](../../03_software/revit/ifc_import_link_reference.md) section 5). The linked `.ifc.RVT` cache can behave differently from the IFC link. Everything that is not a "known reference check" is a guess.

**What fixes it.** Choose a Positioning mode that matches how the file was exported (Revit 2026+); on older versions move the linked instance or use "Acquire Coordinates"; compare with Open IFC (which was correct in the Z bug); update the IFC add-in; keep large offsets out of the IFC; verify with a grid intersection or survey point. The Chinese answer lists seven checks, among them link/category visibility, phase filter, huge coordinates (move the model near the origin) and view range; a second Chinese post says to set the 3D view phase to the latest phase created by the import [src](https://housegear.pixnet.net/blog/posts/3042268210).

**A good assistant should** state clearly what it can and cannot see: it can read the IFC (placement, map conversion, extents) and, with a Revit MCP, read the Project Base Point, Survey Point, True North angle and link instance transform; it cannot guess the add-in bug status. **Clarifying questions:** Revit version and IFC add-in build? Link or Open? Which Positioning option was used? Which coordinate base did the exporter use? Is the model still in the same place after "zoom to fit" in an IFC viewer?

### 3. Revit IFC export writes the wrong position or elevation

**Symptoms.**
- "IFC exports at wrong elevation even when ifcSite is ticked." [src](https://forums.autodesk.com/t5/revit-mep-forum/ifc-exports-at-wrong-elevation-even-when-ifcsite-is-ticked/td-p/11214407) (some users still saw about 20 cm offsets).
- "Models upgraded from Revit 2020 to 2023 export with a -3200 mm Z offset, equal to the PBP vs survey point difference." [src](https://github.com/Autodesk/revit-ifc/issues/780)
- "With shared coordinates rooms are exported high above the rest by the project elevation." [src](https://github.com/Autodesk/revit-ifc/issues/907) (levels with survey point as elevation base; Autodesk acknowledged).
- "Revit doubles up georeferencing data: IfcSite and IfcMapConversion." [src](https://github.com/Autodesk/revit-ifc/issues/177)
- (zh) "IFC导出参数里插入点和项目基点关系" (relation between insertion point and project base point in export parameters) [src](https://www.jianshu.com/p/76e051ccd5eb); Shenzhen SZ-IFC review finds base point, height difference and north empty after export [src](https://zhuanlan.zhihu.com/p/673078056).

**Why.** The exporter writes the same real-world position in several places (map conversion, IfcSite placement/elevation, storey Z). Choosing Shared Coordinates puts real-world coordinates into placements, hence huge numbers and warnings such as "elements are very far from the origin". Level elevation bases (Project Base Point vs Survey Point) can shift only some elements (rooms, levels) [src](https://forums.autodesk.com/t5/revit-architecture-forum/elements-are-being-exported-to-the-wrong-ifc-level/td-p/11927737).

**Fix.** Use a single Coordinate Base for all levels and files; check PBP elevation and angle; prefer PBP + IFC4 map conversion with an EPSG code (see [06 doc](../../01_ifc_basics/06_geometry_placement_coordinates_units.md) section 3.3); after export compare `IfcSite` Z, storey Z and OrthogonalHeight for double counting.

**Assistant behaviour:** compute the absolute Z of a storey from its placement chain, compare to the declared `Elevation` and the map conversion `OrthogonalHeight`, and say if a value looks counted twice. **Ask:** Which Coordinate Base was set? Are all levels based on the same point? Is the receiving party expecting local or georeferenced coordinates?

### 4. Missing, empty or wrong georeferencing data

**Symptoms.**
- "Received an IFC4X3 with IfcMapConversion all zero/NIL and missing axis; is it valid?" [src](https://forums.buildingsmart.org/t/6331) (answer: not invalid, effectively empty).
- "Entering EPSG 3011 in the exporter shows EPSG:6619 in the IFC file." [src](https://github.com/Autodesk/revit-ifc/issues/818)
- "Two products write IfcMapConversion while also using projected coordinates as model coordinates, so the shift is applied twice." [src](https://forums.buildingsmart.org/t/5695)
- "IFC2x3 export has no parameters for EPset_MapConversion and ProjectedCRS" [src](https://github.com/Autodesk/revit-ifc/issues/462); "cannot find my ePset values in Bonsai" (they sit on IfcProject, not IfcSite) [src](https://community.osarch.org/discussion/comment/29556/)
- "IfcProjectedCRS Name is mandatory but UTM 32N + EVRF2007 does not exist in EPSG" [src](https://forums.buildingsmart.org/t/ifcprojectedcrs-epsg-code-not-known/972)
- Local rules: Singapore pre-checks need EPSG:3414 and a SITEBOUNDARY object [src](https://github.com/chunyen93/ifcgref-corenetx).

**Why.** IFC2x3 has no map conversion entity; IFC4 has it, but many tools never read it and exporters can write zeros or duplicate data. The LoGeoRef scale (10 address ... 50 full map conversion) shows how much a file really contains (see [06 doc](../../01_ifc_basics/06_geometry_placement_coordinates_units.md) section 4.1).

**Fix.** IFC4+: one `IfcProjectedCRS` (Name = a single EPSG code, or WKT) and one `IfcMapConversion` with Eastings, Northings, OrthogonalHeight, XAxisAbscissa/Ordinate and Scale. IFC2x3: `EPset_MapConversion` and `EPset_ProjectedCRS` property sets (check IfcProject and IfcSite and tolerate capitalisation variants). Validate in a second tool.

**Assistant behaviour:** report what is present, what is zero, and classify the LoGeoRef level; never state "georeferenced" if the only data are zeros or IfcSite lat/long; do not invent an EPSG code from coordinate magnitudes. **Ask:** Which CRS does the project use (name or EPSG)? Is the project length unit mm or m? Should I write the data or only report?

### 5. Model far from origin: precision, jitter and invisible geometry

**Symptoms.**
- "Models with huge coordinates cause float precision rendering issues; COORDINATE_TO_ORIGIN usually helps but for some it translates with the precision problems baked in." [src](https://github.com/ThatOpen/engine_web-ifc/issues/504)
- "Large-coordinate IFC fine in 2023; in 2024 the selection frame extends to the origin and the 3D view is broken." [src](https://github.com/Autodesk/revit-ifc/issues/712)
- "get_volume loses precision far from the origin: 2.8 m3 wall gives 2.75." [src](https://github.com/IfcOpenShell/IfcOpenShell/issues/9770)
- (en blog) "national-grid mm coordinates making viewers jitter." [src](https://bimcorner.com/same-bridge-three-ifc-files/)
- (zh) "BIM没有地理坐标，需要原点经纬度加xyz旋转角度，原点又不在模型中心" (BIM has no geographic coordinate; origin lat/lon plus rotation needed, origin not at the model centre) [src](https://blog.csdn.net/liyan_gis/article/details/100132931)

**Why.** STEP stores coordinates as text, so the file is exact; the problem is the program that reads it. 32-bit floats keep about 7 digits, so at northing 5,500,000 m the spacing is about 0.5 m (general numeric fact, not from a source). Revit recommends staying within about 16 km of the internal origin.

**Fix.** Small local coordinates plus a map conversion; recentre for viewing and remember the offset; compute volumes relative to a local origin.

**Assistant behaviour:** report bounding box in model units *and* metres, the maximum distance from origin, and a warning above roughly 10 km; when asked to recentre, say that it will change placements, preserve the map conversion, and return the offset vector. **Ask:** Do you want a viewing copy or a deliverable? Should the original stay untouched?

### 6. North and rotation

**Symptoms.** "IFC project north ends up pointing to Revit true north; regression since 2022" [src](https://github.com/Autodesk/revit-ifc/issues/522); "Import an IFC using the angle to true north to influence rotation" (Archicad IFC aligned to grid north) [src](https://github.com/Autodesk/revit-ifc/issues/321); "Where are true, magnetic and grid north stored in IFC4?" [src](https://forums.buildingsmart.org/t/how-is-true-north-and-magnetic-north-stored-in-ifc-and-how-does-it-interact-with-grid-north/3491); "How to identify the orientation of façade elements in IFC?" [src](https://forums.buildingsmart.org/t/how-to-identify-the-orientation-of-facade-elements-in-ifc/4452); (nl) GEO coordination point + BIM origin together equal IfcMapConversion [src](https://github.com/nl-digigo/GeoBIM_Georefereren/issues/5).

**Why.** `TrueNorth` is a 2D direction in the context; once an `IfcMapConversion` exists it is informational, and the map conversion carries the grid rotation via `atan2(XAxisOrdinate, XAxisAbscissa)`. Adding both rotates twice. Revit supports only project north and true north.

**Fix and assistant behaviour.** Report both values in degrees, say which one governs, and never add them; for facade orientation use the map conversion if present. **Ask:** Do you need orientation relative to true north, grid north or project north?

### 7. Georeferenced IFC lands in the ocean (GIS, Cesium, QGIS, 3D Tiles)

**Symptoms.** "Walls modelled with CRS EPSG:27700 ... after converting to GeoPackage it loads mid-ocean in QGIS" [src](https://community.osarch.org/discussion/comment/25984#Comment_25984) (cause in thread: mm project vs metre map units plus a converter ignoring the map conversion; fixed in newer versions); "I export from Revit to IFC4, checked IfcSite, model appears in the middle of the ocean" [src](https://community.cesium.com/t/right-way-to-georeferencing-file-on-cesium/47030); "Cesium ion uses IfcProjectedCRS, not IfcSite" [src](https://community.cesium.com/t/ifc-properties-for-geo-referencing-in-cesium-ion/43003); (zh) IFC to 3D Tiles needs zero-point coordinate and rotation [src](https://blog.csdn.net/GISBox/article/details/149612800).

**Why.** The converter must (a) read the map conversion, (b) apply `Scale` when project and map units differ (mm -> m = 0.001), (c) know the CRS. If it reads `IfcSite` lat/long instead (WGS84, approximate) or ignores everything, the model ends at 0,0.

**Fix and assistant behaviour.** Before export to GIS: read units, `Scale`, `MapUnit`, EPSG; compute the expected world coordinate of the site origin and say whether it is plausible for the stated area (e.g. a UK grid E/N for Britain); suggest corrected Scale. **Ask:** Which tool reads the file (QGIS plugin, Cesium ion, ArcGIS)? Which CRS do you expect?

### 8. Units: 1000x too big or small, feet vs millimetres

**Symptoms.** "IfcConvert to STEP gives a model 1000x too large whatever --length-unit is set to" [src](https://community.osarch.org/discussion/2781/ifcconvert-how-to-control-the-resulting-step-models-scale); "clash annotation lands far away because project units are feet" [src](https://github.com/IfcOpenShell/IfcOpenShell/issues/7178); (zh) "毫米和米单位导致放大1000倍" in a Three.js pipeline [src](https://juejin.cn/post/7691297274821705728); (it) "dove sono dichiarate le unità nell'IFC? il file è valido ma le misure sono sballate" (where are units declared; the file is valid but the measures are off) [src](https://www.ingenio-web.it/articoli/ifc-in-pratica-unita-di-misura-dove-trovarle-e-come-leggerle/); "Systematic RevitIFCUnitBug" [src](https://github.com/Autodesk/revit-ifc/issues/576).

**Why.** Units live in `IfcUnitAssignment` (SI prefix MILLI for mm; `IfcConversionBasedUnit` for feet and inches; US survey foot differs from the international foot). A valid file with the wrong unit declaration is still valid, so validators do not catch it. `Eastings/Northings` use the CRS `MapUnit`, and `Scale` converts.

**Fix and assistant behaviour.** Always read the length, area and volume units first; print numbers with their unit; sanity-check against a door (about 900 mm or 0.9 m); when converting say whether geometry, placements and property values are all converted. **Ask:** What unit do you expect? Do you want the file converted or only the report?

### 9. Units inside property values and exports

**Symptoms.** "Flow in L/s is exported in ft3/s" [src](https://github.com/Autodesk/revit-ifc/issues/444); "Beam System spacing exported as feet / 304.8 in a mm project" [src](https://github.com/Autodesk/revit-ifc/issues/1015); "typed 15 degrees exports as 15.35" [src](https://github.com/Autodesk/revit-ifc/issues/954); "ClearWidth is '1000 mm' text, mapping wants number" [src](https://github.com/LUOaini1213/ifcsg-precheck); (ru) "числовой параметр не переносится, если не запятая" (numeric parameter is not transferred unless it uses a comma) [src](https://habr.com/ru/articles/1098340/); decimal separators in CSV/Excel [src](https://github.com/IfcOpenShell/IfcOpenShell/issues/4290).

**Why.** Revit stores values in internal units and converts per parameter data type; a wrong parameter type gives wrong scale. Text values with units are not numbers. Locale settings change decimal separators.

**Fix and assistant behaviour.** Compare the value's IFC measure type and project unit; flag suspicious factors (304.8, 0.3048, 1000); never silently convert text to numbers, list proposals first. **Ask:** Which unit should the final value be in?

### 10. Elements on the wrong storey; storey list differs from Revit

**Symptoms.** "Elements are being exported to the wrong IFC level" [src](https://forums.autodesk.com/t5/revit-architecture-forum/elements-are-being-exported-to-the-wrong-ifc-level/td-p/11927737); "How to control the IFC building storey a Revit element is mapped to?" [src](https://forums.autodesk.com/t5/revit-architecture-forum/how-to-control-the-ifc-building-storey-a-revit-element-is-mapped/td-p/12688361); "Elements on several levels at equal elevation all land on one IfcBuildingStorey" [src](https://github.com/Autodesk/revit-ifc/issues/285); (de) "elements end up on the wrong floor in IFC" [src](https://bim-me-up.com/ifcbuildingstorey/); (nl) a Dutch guideline asks for one IfcBuildingStorey per floor with sortable names and no extra storeys in the aspect models [src](https://www.digigo.nu/ilsen-en-richtlijnen/bim-basis-ils/3-3-bouwlaagindeling-en-naamgeving) (the Norwegian prompt "etasjene blir dobbelt i IFC" in the test list is synthetic).

**Why.** Revit only exports levels flagged "Building Story" as `IfcBuildingStorey`; elements on other levels are assigned to the next lower storey; the shared parameter `IfcSpatialContainer` can override; two levels with the same elevation merge ([spatial structure doc](../../01_ifc_basics/04_spatial_structure_and_relationships.md) section 2.4).

**Fix and assistant behaviour.** List storeys with names, elevation (project unit and metres) and element counts; compare with the expected list; mark storeys that have no elements or whose elevation duplicates another; for writes, remove the element from the old containment, then assign to the new one; report moved counts and never create a second containment. **Ask:** Which Revit levels should be storeys? What naming convention (BEP/ILS)? Should I only report or reassign?

### 11. Elements outside any storey; incomplete tree

**Symptoms.** "Host walls load with holes but lintels/sills are absent; 324 IfcElements have no spatial containment" [src](https://github.com/IfcOpenShell/IfcOpenShell/issues/9372); "byIfcBuildingStorey does not find all elements (spaces, some roof elements)" [src](https://github.com/ThatOpen/engine_components/issues/653); "A simple cube exported from Blender shows in BIMVision but not in Revit" (needs to be in the spatial tree) [src](https://community.osarch.org/discussion/462/blenderbim-add-on-ifc-export-not-visible-in-revit); (ja) "assign_containerを忘れると床が表示されない" (forget assign_container and the floor does not show) [src](https://zenn.dev/toggle_inc/articles/cf8df02f7b4ba7).

**Why.** Elements need a containment relationship to appear in the tree; viewers read only direct containment and miss elements inside spaces or aggregates; multi-storey elements are contained once and referenced elsewhere.

**Fix and assistant behaviour.** Walk both relationship types (contained and referenced, plus aggregates), report counts of elements with no container grouped by class, and propose containers only after confirmation. **Ask:** Should multi-storey elements (columns, curtain walls, stairs) count on every storey or only the base storey?

### 12. Spatial hierarchy confusion

**Symptoms.** "IfcRelAggregates vs IfcRelNests, parent/child analogy" [src](https://forums.buildingsmart.org/t/4272); (zh) "从IfcProject开始递归，IsDecomposedBy走聚合，ContainsElements拿楼层里的墙门窗" [src](https://www.cnblogs.com/SavionZhang/p/10983394.html); "Tekla exports several IfcBuilding under a site" [src](https://forums.buildingsmart.org/t/application-ifcbuilding/2999); "how to get multiple sites or buildings from Revit" [src](https://bim-me-up.com/ifc-struktur/); "IfcBridge or IfcRoad for wearing surface and kerbs?" [src](https://forums.buildingsmart.org/t/exporting-bridge-elements-to-ifc-4-3-ifcbridge-or-ifcroad/5811).

**Why.** Aggregation builds the Project > Site > Building > Storey tree; containment puts elements into that tree. Revit exports one site and one building. IFC4.3 adds facilities (IfcBridge, IfcRoad...).

**Fix and assistant behaviour.** Print the tree with counts, say what is aggregated and what is contained, explain in plain words; for infrastructure follow facility parts. **Ask:** Do you want the whole tree or one branch?

### 13. National or project rules (SZ-IFC, ILS, CORENET X)

**Symptoms.** (zh) Shenzhen review wants base point coordinates, height difference and north angle; they come out empty [src](https://zhuanlan.zhihu.com/p/673078056); (nl) one IfcBuildingStorey per floor, numeric-sortable names like "-1 kelder", "00 begane grond" [src](https://www.digigo.nu/ilsen-en-richtlijnen/bim-basis-ils/3-3-bouwlaagindeling-en-naamgeving); (en) Singapore pre-check flags elements without storey, missing map conversion, duplicate GlobalIds [src](https://github.com/LUOaini1213/ifcsg-precheck).

**Assistant behaviour.** Ask the user for the rule text or field list; check exactly those fields; answer "present / empty / not representable in IFC" per field; do not apply another country's convention.

### 14. AI/MCP tool defaults on level, unit and rotation

**Symptoms.** (zh) "AI 建牆時沒有樓層參數就取 FirstOrDefault Level，牆建到非預期樓層" [src](https://github.com/shuotao/REVIT_MCP_study/issues/144) (EN: wall creation silently uses the first level when none is given); "reference-object placement ignores Rotation3D; overlay reports about 9 m off" [src](https://github.com/tempalg1n/tekla-mcp-server/issues/44); clash location reported in mm when the project is feet [src](https://github.com/IfcOpenShell/IfcOpenShell/issues/7178).

**Assistant behaviour.** Always pass level and unit explicitly; after any write read back level, elevation and coordinates in the user's unit; refuse to guess a level from "Z=0".

## Edge cases and traps for MCP testing in this area

1. **Unit blindness.** Reporting 6000 as "6000 m" or 0.9 as "0.9 mm". A correct tool output always carries the unit and, for map conversion values, notes that Eastings/Northings are in the CRS `MapUnit` while placements use the project unit.
2. **Scale in map conversion.** Project in mm and CRS in metres needs `Scale = 0.001`. A tool that ignores it puts the model 1000x away in GIS (see problem 7). Test with a file where `Scale` is missing.
3. **Zero or NIL map conversion.** Present but empty (all zero) is not georeferenced. A tool should say "present but empty", not "georeferenced".
4. **Double application.** Projected coordinates in placements plus a map conversion on top. Test with a file where site placement is around 5,000,000 m and `Eastings` is also large; the assistant should flag it.
5. **TrueNorth vs map-conversion rotation.** Must not be added. Ask for both in degrees and the sign convention.
6. **IFC2x3 georeferencing.** No `IfcMapConversion`; look for `ePset_MapConversion`/`EPset_MapConversion` on `IfcProject` and `IfcSite`; names vary in capitalisation. A tool that only looks on `IfcSite` will report "no georeference".
7. **RefLatitude/RefLongitude.** Stored as compound angles (degrees, minutes, seconds, millionths); converting to decimal degrees and handling the sign (the components share the sign of the angle, positive for north/east) is a typical bug. Do not use as the main georeference when a map conversion exists.
8. **Do not infer an EPSG code from coordinate size.** Ask or report "not declared". A UTM-looking number is not a CRS declaration.
9. **Distance from origin.** Compute absolute positions through the whole placement chain (element -> storey -> building -> site), not just the element's local placement. Include a rotated site to catch missing transforms.
10. **Precision far from origin.** Volumes and areas computed from vertices at 5,000,000 m can be wrong by percent; a good tool computes relative to a local origin.
11. **Link IFC vs Open IFC in Revit.** The same IFC can sit at different places or rotations; a Revit MCP must say which path it used and not claim that "the IFC is wrong" when the link path is at fault. Also the linked `.ifc.RVT` cache can differ from the IFC link.
12. **Revit internal units.** The Revit API works in feet internally (general knowledge; a corpus thread says Revit stores internal units and converts on export [src](https://forums.buildingsmart.org/t/supported-data-type-volumetricflowrate-m-h/4189)); a Revit MCP that takes "6000" must be explicit that it means mm and convert. The same applies when reading levels' elevations.
13. **Level defaults.** Creating a wall without a level must not silently use the first level at Z=0. Test with a prompt that names no level and one that names a non-existent level (expect an error or a question, not a guess).
14. **Building Story flag.** Elements on unflagged levels are silently reassigned to a lower storey in the exported IFC; the Revit view of "which level" and the IFC view differ. A comparison tool should name both.
15. **Equal-elevation storeys.** Two levels at the same elevation merge in some exporters; a tool listing storeys by elevation may collapse them. Test with duplicates.
16. **Contained vs referenced.** Multi-storey elements are contained once and referenced elsewhere; counts per storey differ depending on which relationships a tool reads. Ask the user which count is wanted.
17. **Elements inside spaces.** Furniture or equipment contained in an `IfcSpace` has no direct storey container; "elements on level 2" must climb the tree.
18. **Move/assign writes.** Moving an element between storeys must remove it from the old `IfcRelContainedInSpatialStructure`; adding a second containment creates an invalid file. Creating a storey needs `IfcRelAggregates`, not containment.
19. **Preserving georef on edits.** Extracting elements, merging or recentering with some tools drops or rewrites georeferencing (reported for IfcPatch ExtractElements) [src](https://github.com/IfcOpenShell/IfcOpenShell/issues/8199); after any write the tool should re-read the map conversion.
20. **Multi-file questions.** Comparing files requires all of them to be loaded; the assistant should say which file it could not open and not invent values for it.
21. **Language.** Reply in the user's language (ru, zh, ja, ko, de...) but keep IFC entity names, GlobalIds and numbers unchanged; do not translate "IfcBuildingStorey".
22. **Silent success.** Writes that "succeed" but do not persist (reported for some MCP servers) – always read back from the file or the Revit document and show the values.
