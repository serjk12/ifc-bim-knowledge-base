# The 100 most common and most costly IFC and Revit-IFC pain points

**Last researched: 2026-11-06.** Built from the whole raw research set (wave 1) and cross-checked with the 17 topic documents in [by_topic/](by_topic/).

## In plain words

IFC is a neutral file format that lets different building-design programs exchange a 3D building model (walls, doors, pipes) together with data (fire rating, area, material). Revit is the most widely used design program; it has its own IFC "exporter" (the part that writes the file) and "importer/linker" (the part that reads someone else's file). Most everyday trouble happens at those two doors: something goes in, something different or nothing comes out.

This page lists the **100 problems people ask about most**, ordered from most common and most costly to least. For each one it shows:

- how real people write it in English, in Russian and in a third language (so a tester can imitate the voice),
- how widespread it is in the collected data,
- why it happens in one sentence,
- the usual fix in one sentence,
- a link to the topic document with the full discussion and more real questions.

Use it three ways: (1) **pick test requests** from the top rows, (2) **judge answers** by comparing with the "root cause" and "usual fix" columns, (3) **find the right topic document** for details through the last column.

## How the ranking was made (and what the numbers mean)

- **Data**: 3,592 records in 78 files: 2,304 real questions and 1,288 synthetic (invented, labelled) prompts. Real records by language: en 1,827, zh 170, ru 109, ja 59, es 34, it 29, de 23, nl 21, no 13, ko 9, fr 4, pt 1 (sk and vi one each). Portuguese is almost entirely synthetic (pt 29 and pt-BR 15 synthetic prompts, one real record).
- **Frequency signal** (column 4): for every problem I counted the *real* records whose topic tags and multilingual keywords match, then the distinct source pages ("threads"), the languages they are written in, and the most frequent asker roles. "+N synthetic" is how many of the invented test prompts touch the same problem. These are **keyword tallies, not a survey**: one GitHub issue often produces several records, rows overlap, and a matching record is not always a perfect match. Read them as relative size.
- **Score**: threads x impact weight x (1 + 0.08 per extra language, up to 8) + 0.15 per synthetic prompt. Impact weight: 1.5 = the file is unusable or data is lost silently, 1.25 = a wrong result that may go unnoticed, 1.0 = friction, 0.75 = niche. The weights are my editorial judgement.
- **Hand adjustments**: eight rows sit below the natural cut and were added on purpose so that every topic document is represented and the AI-specific problems stay visible: #99, #100, #95, #96, #97, #98, #88, #94. Several lower-scoring candidates were merged into neighbours (for example grey MEP pipes into the colour row).
- **Bias to keep in mind**: 79% of real records are English and 1,157 of those 1,827 are GitHub issues, so exporter and library bugs look more frequent than they are in daily office life. Questions about authority submissions, local classification and "is it mandatory" are under-counted in English and dominate in zh, ru, es, it, ko and no.
- **Examples** are the data's *paraphrases* of real posts (original language, with an English gloss after "="), not verbatim quotes. Each links to its source page by record id. Examples marked *(synthetic, `id`)* are invented test prompts inspired by real patterns, shown only where no real record of that language fits. In the RU column 51 examples are real, 46 are synthetic and 3 rows have no Russian record; the third-language column has 5 synthetic examples and 3 rows without a record.

## Mini glossary for non-BIM readers

| Term | Plain meaning |
|---|---|
| IFC class (IfcWall, IfcDoor) | The "kind of object" label inside the file. `IfcBuildingElementProxy` is the "unknown object" label ("proxy"). |
| Property set (pset), property | A named group of data attached to an object (for example `Pset_WallCommon` with `FireRating`). |
| Quantities (Qto, base quantities) | Measured numbers such as area and volume stored with the object. |
| GlobalId (GUID) | The 22-character id of each object; used to track an object between versions. |
| Exporter / Link IFC / Open IFC | Revit's IFC writer / the way Revit reads an IFC as a read-only reference / the way it converts it into its own objects. |
| IFC2x3, IFC4, IFC4.3 | Versions of the format. IFC2x3 is the oldest one still common, IFC4.3 adds roads, rail and bridges. |
| MVD / view (Coordination View, Reference View, Design Transfer View) | A "profile" that says which part of IFC a particular exchange uses. |
| Georeferencing, map conversion | Tying the model's local zero point to a real-world coordinate system. |
| IDS | A machine-readable list of data requirements that a checker can test an IFC against. |
| BCF | A small file for sending issues (with camera view and object ids) between programs. |
| CDE | Common data environment: the shared project storage where models and issues are exchanged. |
| COBie | A spreadsheet-style handover format for facility management. |
| MCP | The plug-in standard that lets an AI chat connect to tools such as a Revit or IFC server. |

More terms: [../08_glossary/glossary_multilingual.md](../08_glossary/glossary_multilingual.md), [../08_glossary/abbreviations.md](../08_glossary/abbreviations.md), and the IFC basics in [../01_ifc_basics/01_what_is_ifc_and_versions.md](../01_ifc_basics/01_what_is_ifc_and_versions.md).

### Differences worth knowing

- **"Will the authority accept my file?" is a mainstream problem outside English.** In the self-check/authority-portal row (#4) the tally is zh 23, en 15, ru 12, ja 7; the related rows are #26, #45, #72. English asks are mostly about the tool bugs behind a rejection.
- **Local classification systems differ and are checked differently**: NL-SfB/NLCS (nl), KSI/MSSK codes (ru), Uniclass (UK), DIN 276 (de), plus national handover specs (#48, #21, #54). A request that names "Uniclass" or "NL-SfB" is a regional signal.
- **Coordinate conventions are national**: the Singapore portal material asks for SVY21 (EPSG 3414) and the Shenzhen/China material for base-point and north fields (CGCS2000 is named in [by_topic/regulations_permits_contracts.md](by_topic/regulations_permits_contracts.md)); the synthetic Russian and Japanese prompts, inspired by real posts, talk about the local coordinate system (МСК) and the Japanese plane rectangular zones. The English "shared coordinates vs project base point" wording is Revit-specific, and the same trouble appears in all languages (#8, #38, #58, #57).
- **Software mix changes the problem**: Russian and Chinese posts discuss Renga, nanoCAD, SCAD, Lira and Tekla exchanges (#13, #25, #92, #93); English posts are mostly Revit, Archicad, Tekla and open-source tools (IfcOpenShell, Bonsai, That Open web-ifc, xBIM).
- **Text encoding is a multilingual problem** (#24, #83, #73): ten languages appear in the row; the 25 English records are mostly bug reports about Chinese, Cyrillic, umlaut or accented text, and non-ASCII file names or paths break tools that English-only users never notice.
- **Who asks differs**: English is developer-heavy (597 of 1,827); developers are also the largest group in Chinese and Japanese (57 of 170 and 21 of 59); Russian has the most structural engineers (22 of 109); German records come mostly from coordinators (11 of 23); Spanish records come from students (9 of 34) and BIM managers (7).
- **The "what is IFC / is it mandatory / where do I start" questions are asked in nearly every language** (#69, #26, #88), so a test set should include some plain beginner prompts in each language, not only expert troubleshooting.


## What this means for MCP testing

The tester should assume these points when inventing requests and judging answers. Row numbers refer to the table above.

1. **Seed the test set from the top rows, in the voices shown.** The first 15 rows (big files, missing elements, files that will not open, authority self-check, property editing, openings, IFC4.3, georeference, IDS, AI-to-Revit connection, GUID churn, browser limits, export settings, proxies) cover most of what people actually ask. Use the EN/RU/other examples as tone references and vary details (class, storey, version) instead of copying them.
2. **People describe symptoms, not tasks.** "Half the model is gone", "the IFC is huge", "everything is a proxy" (#2, #14, #15). A good answer first measures (counts per class, size by class, header/schema), then explains. Penalise an answer that lectures without looking at the file.
3. **Many phrasings leave out the facts the answer needs** (Revit version, exporter build, IFC version/view, where the file is going). The good behaviour is to read what the file itself says and ask one short question for the rest, not to guess (#34, #13, #7).
4. **Separate "problem in the file" from "problem in Revit's settings".** An IFC-only server cannot change Revit export options. Rows such as #42, #43, #35, #19, #55 should end with the Revit-side step and an honest "I can only see the file", not a claim that it fixed the export.
5. **Reward honest UNKNOWN.** The header can lie about version/view, empty values are not the same as false, a missing quantity is not zero (#20, #52, #96, #78). Answers should report PASS / FAIL / UNKNOWN with the evidence (class names, GlobalIds, counts) and say which method produced a number.
6. **Always state units and coordinates.** Units off by 1000x, feet vs millimetres, far-from-origin precision and CRS mix-ups recur in many languages (#44, #97, #8, #46, #57). Check that every length, area and position comes with its unit and that map conversion/scale was read.
7. **Check type and occurrence.** Values live on the type, the instance, the layer set or a constituent set (#56, #76, #75, #61). A tool that reads only one level will report "missing" wrongly; judge answers on whether both were consulted.
8. **Never invent names.** LLMs make up property-set names and values (#62, #99). A correct answer quotes the names found in the file or the standard, and says when a name is not in the schema.
9. **Writes must be previewed, idempotent and read back.** Editing properties, classifying, fixing proxies or deleting duplicates (#5, #87, #90, #82) should show a dry run, ask before destructive changes, write to a new file or a transaction, and verify afterwards. Retrying after a timeout must not duplicate elements.
10. **Test the plumbing too.** Connection failures, version mismatches, hidden defaults (first level, Z=0) and errors hidden in dialogs are real and frequent (#10, #100, #87). Include prompts that arrive while the server is not ready and judge the clarity of the error and the recovery steps.
11. **Heavy files and time limits.** Large models, long exports and 60-120 second client timeouts (#1, #30, #12, #55, #14) call for staged answers: quick summary first, narrow queries, a clear "this takes minutes" message, never a silent hang.
12. **Do not claim approval or legal outcomes.** For authority checks, mandates and contracts (#4, #26, #45, #72, #98) the answer should ask for jurisdiction and the rule text, compute what is checkable (PASS/FAIL/UNKNOWN), and never say "the authority will accept this".
13. **Multilingual realism.** Mix Cyrillic and CJK property names, file names with non-ASCII paths, `\X2\` escapes and decimal commas (#24, #83, #73, #78). Also test class names typed in odd casing and local slang ("ифс", "ревит", "проксики") as in [../06_how_people_write/](../06_how_people_write/).
14. **Expect beginner and concept questions in every language** (#69, #88, #77, #79, #80): "what is IFC", "is IFC lossless", "what is a CDE". A good answer is short, concrete, and uses the user's own file as the example when one is loaded.
15. **Compare and track changes.** GUID churn and diffs (#11, #22) need matching by GlobalId with a stated fallback (type + name + position) and a confidence for each match; judge whether the answer admits uncertain matches.
16. **Cross-tool disagreement is normal.** Different viewers, kernels, clash engines and IDS checkers give different answers (#16, #39, #9, #37). Reward answers that name the engine and version, offer a second-tool check, and avoid declaring one tool "right".
17. **Make some tests unanswerable on purpose.** Examples: ask for stair width where no such property exists, rebar weight where rebar is not modelled, a georeference in an IFC2x3 file, a quantity the exporter never wrote (#45, #60, #8, #20). The correct behaviour is to say it is not in the file and offer a computed alternative clearly labelled as computed.
18. **Weight the test mix by frequency, then add the rare-but-dangerous ones.** Use the ranks as sampling weights, but also keep a small fixed set of the AI-specific traps (#99, #100, #87, #10) because the data under-represents them and they are where an MCP server can do damage.
19. **Give each test a "known file state".** Most problems above can be reproduced from a specific property of the file (proxy count, missing Qto, no map conversion, raw non-ASCII bytes). Pair every prompt with the file feature it relies on, using the sample files in [../04_open_source/sample_ifc_files.md](../04_open_source/sample_ifc_files.md), so a judge can verify the answer against the file.
20. **Judge on evidence, not eloquence.** An answer that matches the "root cause" and "usual fix" columns but cites no class counts, ids or tool output should score lower than a shorter answer with verifiable details. See [../07_mcp_testing/evaluation_rubric.md](../07_mcp_testing/evaluation_rubric.md).
